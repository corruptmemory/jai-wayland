# entire graph and Jai: findings, and why the wiring was removed

> 2026-10-29. `entire graph setup` was run in this repo, then reverted the same day: Graph cannot
> parse Jai, so the agent guide it installs ("make a Graph query your first action for every code
> lookup") sends agents into an index that holds none of this repo's Jai code. Fixing that is its
> own project (see the end of this note); it does not belong here.

## What Graph sees in this repo

Measured with entire-graph v0.6.0 (Entire CLI 0.12.2) at commit `9d4bad1`:

- `.jai` is in neither of Graph's language tables: not the tree-sitter one
  (`internal/sem/parser.go`, `treeSitterLanguages`) and not the inventory-only one
  (`internal/sem/inventory_languages.go`). `entire graph capabilities --json` lists no "Jai".
- Graph indexed **10 source files**: 6 C, 2 C++, 1 Bash, 1 GLSL. The repo has 389 tracked `.jai`
  files, about 101K lines, and none of them are indexed.
- `entire graph health` reports "degraded", but only because of a parse error in
  `modules/Vulkan/source/vulkan_core.h`. It says nothing about the `.jai` files:
  `unsupported_but_detected_language_hints` is empty. So the blindness is silent.

An empty Graph result for Jai code therefore means "not indexed", never "no callers".

## Why there is no quick fix

- **No plug-in point.** Languages are compiled-in Go maps. There is no config file to add one,
  Graph never downloads grammars (its no-egress design rules that out), and its SCIP support is
  export-only, so facts cannot be fed in from outside.
- **No tree-sitter grammar.** `~/projects/tree-sitter-jai` records why one is not viable: Jai's
  braceless control-flow bodies (`if a * b  x;`) need GLR ambiguity that blew the parser up to
  18,448 states (about 1.6× C++), and tree-sitter's static conflict resolution defeats the
  workarounds.
- **A fork does drop in.** `entire graph` runs the first `entire-graph` binary on PATH, the way git
  finds its subcommands, and the code is MIT-licensed, so `go install` from a fork replaces the
  stock binary.

## Precedents inside entire-graph

- **Groovy has a parser that is not tree-sitter.** `internal/sem/groovy.go` (1,198 lines) exists
  because the Groovy tree-sitter grammar failed on real code. Its header says that once comments
  and string literals are masked out, a line-and-brace scan "recovers types, methods, and fields
  reliably". SQL (`internal/sem/pgsql`) is a second grammar-less semantic language.
- **Calls are already found by regex.** Even grammar-backed languages get their CALLS edges from
  per-language regexes run over masked bodies (Zig, Julia and Lua in `internal/sem/call_scanners.go`).
  A Jai scanner would not be held to a stricter standard than Zig already meets.
- **The test gate.** Every semantic language needs a fixture under `internal/sem/testdata/langmatrix/`;
  `TestLanguageExtractionMatrix` fails without one.

## Options, cheapest first

- **A. Inventory-only registration.** One line, `".jai": {language: "Jai", inventoryOnly: true}`,
  upstreamable as is. The files get counted and health becomes honest, but each file yields one
  whole-file `document` symbol: no procedures, no calls. Worth sending upstream together with a bug
  report about health saying nothing about extensions it does not recognize.
- **B. A structural scanner in Go, on the Groovy model.** Tree-sitter's trouble with Jai is in
  expressions; a scanner that only extracts declarations never has to resolve them, and Jai's
  declaration shapes (`name :: …`, `name : T = …`, `name := …`) are unusually regular.
  - Mask pass: nested `/* */`, single-line `"…"`, `#string END … END` here-strings, `#asm` blocks.
  - Brace-depth walk that classifies `name :: (` (procedure), `:: struct` / `enum` / `enum_flags` /
    `union` (types), `:: #type` (alias), `operator X ::` (overload), `#import` / `#load` (imports),
    `#scope_*` (visibility).
  - A Jai entry in `call_scanners.go` for `ident(` and `Module.ident(`.
  - Limits: name-only call resolution (polymorphs, `using` and overloads collapse by name), nothing
    generated by `#insert` / `#run` is visible, and both branches of an `#if` count.
- **C. Compiler-backed facts.** A metaprogram receives `Message_Typechecked`, and every `Code_Ident`
  carries `resolved_declaration` (`~/jai/jai/modules/Compiler/Compiler.jai:763`), so a build plugin
  could emit exact definitions and references, `#insert`-generated code included. But Graph indexes
  the committed tree without running anything, so this needs a fork that reads a facts file produced
  by a build; upstream would not take it. It also sees only the `#if` branches compiled for one target.
- **D. A recursive-descent Jai parser in Go.** Tree-sitter's limits are specific to LR parsing; a
  recursive-descent parser handles braceless bodies by reading the condition until the next token
  cannot continue the expression, which is what the Jai compiler and the Jails LSP's `jai_parser` do.
  It gives real scopes (locals, nested procedures), so far fewer false call edges.

## Direction (decided 2026-10-29)

Not in this repo. A new project, possibly built with Entire's own tooling and its own repo, takes
**A and B first, with D as the target**.

D has one requirement the options above do not capture: Jai is still changing between compiler
releases, so the parser has to cover **the language over time, not one version of it**. Its accepted
syntax is therefore larger than any single release's. When a new compiler ships, the parser gains
the new syntax as the target while still recognizing the syntax that release deprecated, ideally
flagging it as deprecated rather than failing on it. That makes the parser itself versioned against
compiler releases, much as the `jai-language` skill's compendium is re-proved on every bump, and it
suggests the same discipline: a corpus per compiler version that the parser must accept, with the
deprecated constructs marked.
